## Come si chiude un task

`verify` quando e' fatto, `done` solo dopo una verifica AVVERSARIALE, perche'
`done` e' terminale. Avversariale vuol dire una MISURA, non una rilettura:

- togliere il solo COMPORTAMENTO e vedere il test rosso. Se togli la firma o il
  campo stai misurando la compilazione, non il fix;
- un test che passa con e senza il fix e' una falsa guardia. Ne ho scritte due
  in questa sessione, entrambe trovate dall'attacco e non dalla rilettura: il
  test del budget di C7 asseriva sul tempo trascorso con un margine cosi' largo
  da restare verde anche con budget per chunk (riscritto per asserire su cosa
  il budget ha COMPRATO, cioe' quanti chunk hanno un vettore); e il test della
  guardia del database passava una URL la cui password `str()` maschera in
  `***`, quindi l'autenticazione falliva e la guardia taceva correttamente
  senza che nulla fosse sotto misura;
- se l'attacco non produce rosso, chiediti se hai colpito il livello giusto;
- controlla PERCHE' l'attacco e' rosso. Uno dei miei e' finito rosso con
  un'eccezione del finto embedder invece che con l'asserzione: era il log
  catturato di una scrittura voluta, ma andava guardato;
- scrivi cosa hai attaccato e cosa e' sopravvissuto, non solo la conclusione.

Il lavoro fatto si scrive come commento sul task (`add_comment`), non solo nel
commit: e' li' che la prossima sessione lo trova.

## Trappole degli strumenti, gia' pagate

- `get_task` vuole lo UUID INTERO; un prefisso da' "badly formed hexadecimal
  UUID string". Risolvi prima con `list_tasks(q=...)`.
- `list_tasks` prende `tag_id` e `state_id`, non `tag_ids` / `state`.
- `set_task_state` vuole `expected_version`, e il workflow rifiuta
  todo -> verify: si passa da `in_progress`. Stati:
  todo `181c039a-8536-43a0-9281-ce3fcba83f00`,
  in_progress `7cb9de9f-eb3b-4195-bbfd-e67a39debecf`,
  verify `4185cb12-3462-4dd7-92dd-870e1ecf1bee`,
  done `f44a26b1-609a-4f71-b8a8-79d4f990847c`.
- Un task nuovo creato via MCP non nasce nel progetto: `move_task_to_project`.
- Se scrivi un Makefile con un heredoc Python, le continuazioni `\` a fine riga
  spariscono (Python le mangia dentro una stringa non-raw). Scrivi il blocco
  con un heredoc di shell.

## Gate locali (== CI)

    uv run python -m pytest api/tests core/tests cli/tests -q
    uv run mypy core/src api/src mcp/src worker/src sdi-inbound/src
    uv run ruff check . && uv run ruff format --check .
    uv run python scripts/gen_mcp_coverage.py --check
    cd web && pnpm check:api-types && pnpm exec vitest run

Se tocchi la PRIMA RIGA del docstring di un tool MCP, rigenera
`docs/mcp-coverage.md`. Se cambi uno schema API, `cd web && pnpm gen:api`.

**La CI e' la misura autorevole** e gira la suite in ~11 minuti su una macchina
pulita. Un push NON la fa scattare:

    git push origin v2.3 && gh workflow run ci.yml --ref v2.3

Non portare un task a `done` prima che la CI abbia risposto. In questa sessione
la suite locale completa e' stata UCCISA DAL SISTEMA per memoria (non da un
fallimento) a meta' strada: se succede, gira i moduli toccati a lotti e lascia
il resto alla CI, non concludere niente dal kill.

Occhio alle guardie di FORMA: `test_neither_projection_has_lost_a_field_it_used
_to_carry` e il set di chiavi in `test_mcp_retrieval_meta` asseriscono la forma
INTERA, quindi aggiungere un campo le fa fallire per costruzione. Si aggiorna
la forma attesa, non si rilassa l'asserzione.
